# RF01 and local API continuity across ordinary deployments

This change is based on main51e6a122 and carries only the runtime code already activated for RF01 and local API auth, plus focused tests. It does NOT merge the ERS preparation branch wholesale: no SLM changes, OS rehearsal, MCP, RAG, tenants activation or model switch.

The regular PM2 ecosystem now reads service-scoped activation settings from ~/jarvis-estado/secrets/runtime-env.json, schema1. This is a server-only0600 file, never versioned. Supported keys are restricted to the existing RF01/SQLite settings on WhatsApp and local API bearer/loopback settings on API. Cross-service token sharing, arbitrary new flags, remote Redis, nonloopback API or divergent DB paths are rejected. ~/jarvis-estado/secrets/runtime-env.required marks an activated install so accidental config absence fails before producers stop instead of silently disabling the queue. On a new install with neither file, historical inactive defaults remain.

Activation config is built from the current verified private per-service PM2 config, not from a guessed token, generic shared .env or current shell. It retains the same jarvis.db, Redis credential and API token. There is no rotation or disclosure. Both API and WhatsApp still get their ordinary existing .env configuration when the application imports its config. The private file is not an API itself and creates no new audience.

Deployment preflight loads the candidate ecosystem before the existing stopped backup/cutover. It must not print the ecosystem object (contains secrets). The existing full suite/critical gate and consistent encrypted backup remain. Ordinary main deployments use reviewed source with the same RF01/API implementations, and the ecosystem keeps per-service flags. No shortcut to skip tests, no global CI disable, no automatic database restoration.

Before first main cutover: privately snapshot current runtime config, create0600 runtime-env.json and the required marker, verify candidate ecosystem yields exact currently effective settings (in memory, no secret output), compare RF01/API runtime file hashes, review the delta and keep current release as rollback code. The old business DB must never overwrite newer state. Pending/en_curso/uncertain entries must be retained and not replayed by a legacy worker. Observe current deployment to stable PM2, authenticated API200/negative401, local binds, Redis AOF and organic-row counters. No fake real-channel events/model calls to make E2E claims.

Updated four historical tests preserve their original checks while reflecting new contracts: ready runtime+channel before ACK; migration versions now1..10 (numeric sorting for10), still no duplicate application, row loss or FK violation. Initial full suite found these four stale expectations; they are not hidden by the95% noncritical threshold.

The post-cutover health probe reads API-only credentials from the same ecosystem in memory. It requires authenticated200 with ok:true plus401 for absent and wrong tokens. A fresh unconfigured installation must return the existing disabled503 contract. No token goes through shell arguments, request headers or raw response bodies in logs. The deployment harness scenarioF uses a real local HTTP stub and private0600 runtime config with no API token in shared.env; its synthetic backup and PM2 remain isolated.
